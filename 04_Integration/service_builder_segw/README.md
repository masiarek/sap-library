# The Gateway Service Builder (SEGW): the model is the source, the classes are generated

**Level:** 201 · for ABAP developers, and for anyone who has to read an OData service somebody else built

**One line:** A SEGW project is a data model and nothing else; from it the Service Builder generates the model provider class that answers `$metadata`, the data provider class with one method per entity set and operation, and the two names a Gateway hub registers; every line you write goes into the two `_EXT` subclasses, because the next generation rewrites the other two and leaves the `_EXT` pair alone, including a redefinition whose method has meanwhile disappeared.

## Where the Service Builder sits

SAP Gateway is two software components with two namespaces, and almost every transaction on this page belongs to one of them:

| Component | Namespace | What lives there |
|---|---|---|
| Backend enablement (IW_BEP, in S/4HANA part of the ABAP platform) | `/IWBEP/` | The Service Builder `SEGW`, the generated classes and their superclasses, the backend registration of models and services, the backend error log `/IWBEP/ERROR_LOG`, the backend cache `/IWBEP/CACHE_CLEANUP` |
| Gateway foundation (IW_FND, the *hub*) | `/IWFND/` | The service catalogue `/IWFND/MAINT_SERVICE`, the Gateway client `/IWFND/GW_CLIENT`, the hub error log `/IWFND/ERROR_LOG`, the hub cache `/IWFND/CACHE_CLEANUP`, the ICF node `/sap/opu/odata/sap/<service>` that HTTP reaches |

The hub can be a separate system that reaches the backend over RFC through a *system alias*, or the same system (*embedded deployment*, with the alias `LOCAL`). Either way the request path is the same: HTTP hits the ICF node in the hub, the hub finds the service in its catalogue, follows the alias to the backend, and the backend runs the data provider class. [Registering a service in the hub](../registering_a_service_in_the_hub/README.md) is the second half of that path; this page is the first.

## The project is a data model

A project in `SEGW` has four nodes, and only the first one is yours:

| Node | What it holds |
|---|---|
| **Data Model** | Entity types (a name, properties with an EDM type, a key, an optional ABAP structure and field per property, flags such as creatable, updatable, nullable, filterable, sortable), complex types, associations (two entity types, a cardinality, a referential constraint), navigation properties, entity sets (one or more per entity type, each with its own flags), function imports |
| **Service Implementation** | One entry per entity set and operation, which is where a mapping to an RFC or BOR method would be maintained; empty for a hand-coded service |
| **Runtime Artifacts** | The four classes, the technical model and the technical service, once generated |
| **Service Maintenance** | The hub systems the service is registered in, and the registration itself |

The model can be filled four ways: typed in by hand; imported from a Dictionary structure, an RFC interface or a BOR object, or from an EDMX file; *redefined* from an existing service, a BW query, an SPI object or a GenIL component; or *referenced* from a CDS view (*Reference Data Source*), which is how the delivered S/4HANA APIs are built, see [API_BUSINESS_PARTNER](../api_business_partner/README.md). Whatever the route, the result is the same kind of model, and the generator reads nothing else.

Three things to read off that output:

- **The class prefix is `ZCL_` plus the project name**, so a project called `ZBP_IDNUMBERS` gets classes called `ZCL_ZBP_IDNUMBERS_…`, with the Z twice. The technical model and service are the project name with `_MDL` and `_SRV`.
- **A name over 30 characters cannot be created**, so for `API_BUSINESS_PARTNER` the extension classes had to be named by hand, and `GWSAMPLE_BASIC`'s classes are `/IWBEP/CL_GWSAMPLE_BAS_…`, with the project name clipped. The Runtime Artifacts node is where the real names are; never derive them.
- **The namespace in `$metadata` is the technical service name**, and the service document's URL carries the *external* service name the hub registered, which for a customer service is the same string, see [Registering a service in the hub](../registering_a_service_in_the_hub/README.md).

## What generation derives: `$metadata`

The model provider class (MPC) has one method, `DEFINE`, that builds the model at runtime, and the framework serialises it as the EDMX document above. The mapping from a Dictionary type to an EDM type is the Service Builder's default when a property is bound to an ABAP field; it can be overridden per property, and `Edm.Boolean` for a CHAR 1 flag is the override everyone makes:

| Dictionary type | EDM type | Facets the generator adds | How sure |
|---|---|---|---|
| CHAR, SSTRING, STRING, NUMC, CLNT, LANG, CUKY, UNIT | `Edm.String` | `MaxLength` for the fixed-length ones | sure |
| DATS | `Edm.DateTime` | `Precision="0"`, `sap:display-format="Date"` | sure |
| TIMS | `Edm.Time` | `Precision="0"` | sure |
| INT1, INT2, INT4, INT8 | `Edm.Byte`, `Edm.Int16`, `Edm.Int32`, `Edm.Int64` | | sure |
| DEC, CURR, QUAN | `Edm.Decimal` | `Precision` = Dictionary length, `Scale` = decimals; `sap:unit` naming the CUKY or UNIT property when the model says so | fairly sure on the facets |
| FLTP | `Edm.Double` | | sure |
| RAW, RAWSTRING | `Edm.Binary` | | sure |
| CHAR 1 chosen as `Edm.Boolean` | `Edm.Boolean` | the framework converts `X` and space | sure |

Key properties come out `Nullable="false"`; the entity set's checkboxes (creatable, updatable, deletable, pageable, addressable, searchable, subscribable, requires filter) come out as `sap:` attributes on the `EntitySet` element. Those attributes are a statement to the consumer, and a Fiori elements application reads them; which of them the Gateway runtime itself enforces differs by attribute and release, so the verification table below tests two of them rather than this page asserting it.

## What generation derives: the data provider class

The data provider class (DPC) gets five methods per entity set, named after the entity set in upper case: `<SET>_GET_ENTITYSET`, `_GET_ENTITY`, `_CREATE_ENTITY`, `_UPDATE_ENTITY`, `_DELETE_ENTITY`. Each one is generated with a single statement that raises the *not implemented* exception. The class also inherits the framework interface `/IWBEP/IF_MGW_APPL_SRV_RUNTIME`, and its generated implementations of that interface are the dispatcher: a `CASE` on the entity set name that calls the method above and copies the result into the framework's data reference.

The `_EXT` class inherits from the DPC and is empty. Everything you write is a redefinition there, and this is the whole design: the generator owns the DPC and may rewrite it any time the model changes; it never touches the `_EXT` class; and the framework instantiates the `_EXT` class, so your redefinition wins over the generated stub. The same holds for the MPC and `MPC_EXT`: a redefinition of `DEFINE` in `MPC_EXT` (calling `super->define( )` first) is where annotations and conversion exits are added in code.

The method names also explain a limit you meet on long entity set names: the name is the set in upper case plus `_GET_ENTITYSET`, fourteen characters, so a set of more than sixteen characters gives a method name over 30, and the generator has to shorten it. Read the shortened name in the generated class; do not guess it.

## A request reaches a method: what the framework does and what it leaves to you

Section 5 of the output follows twelve requests from the URL to the method. The rule it shows is the one most worth keeping:

- **The framework parses the URL for you**: the entity set, the key predicate (`it_key_tab`), the navigation path and its source keys, the query options, and the function import name, which goes to `EXECUTE_ACTION` with the parameters as a table.
- **It applies `$select` and `$format` after your method returns**, serialises what you returned, counts it for `$count`, and resolves `$expand` by calling the navigation target's method once per entity you returned, unless you redefine `GET_EXPANDED_ENTITY` or `GET_EXPANDED_ENTITYSET` and return the deep structure yourself.
- **It applies nothing else.** `$filter` arrives as `it_filter_select_options` (ranges) and as the filter string; `$top` and `$skip` as `is_paging`; `$orderby` as `it_order`; `$inlinecount` as a flag. A hand-written `GET_ENTITYSET` that ignores them returns the whole table, and the consumer sees no error, only wrong data. This is the single most common defect in a Service Builder service, and it is not a bug in the framework: the framework cannot know which `SELECT` you would have written.

A service whose entity sets are *referenced* from CDS views behaves differently: there the generated data provider delegates to the SADL framework, which turns those same options into one `SELECT` on the view, with the filter, the paging and the sort pushed to the database. That is why the delivered APIs filter correctly without anybody having coded a `GET_ENTITYSET`, and why a hand-coded service and a CDS-based one answer the same URL differently when the method was left incomplete.

## Generating again: what survives

Section 6 of the output renames an entity set and generates again. The DPC is rewritten with the new method names. The `_EXT` class still holds a redefinition of the old method, which the superclass no longer has, and a class with a redefinition of a non-existent method does not activate. The fix is to rename or delete the redefinition; the lesson is to rename entity sets before implementing them, not after. The same applies when an entity set is deleted, and, with less drama, when a property is renamed: the structure type `TS_<ENTITY>` in the MPC changes, and code in the `_EXT` class that named the old component stops compiling.

After every generation, `$metadata` served by the hub may still be the old one: both the hub and the backend cache the model. Clearing the two caches (`/IWFND/CACHE_CLEANUP`, `/IWBEP/CACHE_CLEANUP`) is the first thing to do when a property added in `SEGW` does not appear in the Gateway client.

## Where S/4HANA differs

The Service Builder is an OData V2 tool and stays one. Three things have grown up beside it:

- A CDS view annotated `@OData.publish: true` becomes a service called `<view>_CDS` without a project, with its classes generated under `CL_<view>`.
- The ABAP RESTful application programming model (RAP) defines a *service definition* and a *service binding* in ADT; the binding is OData V2 or V4, and the V4 ones answer under `/sap/opu/odata4/`. The Service Builder has no part in it.
- The delivered `API_*` services of S/4HANA are still `SEGW` projects on CDS reference data sources, which is why the project in the screenshot this page started from can be opened and read.

So `SEGW` is where you read and extend the classic services, and where a new OData V2 service with hand-written logic still gets built; a new service on a CDS model is written in ADT.

## The classic bugs

1. **The method you did not redefine.** The consumer calls an operation, the generated stub raises *not implemented*, and the error log in the hub names the method. Redefine it in the `_EXT` class.
2. **`$filter` ignored.** The model marked the property filterable, the method never read `it_filter_select_options`, and every call returns everything. See above.
3. **Stale `$metadata` after a model change.** Two caches, two cleanups.
4. **The orphaned redefinition** after renaming an entity set, as in section 6.
5. **Registered in the backend, not in the hub**, or registered with the ICF node inactive: the URL answers *not found* although `SEGW` shows the service as generated. The next page.
6. **An initial date.** A DATS field holding `00000000` has no `Edm.DateTime` value. For a nullable property the framework returns `null`, which is what `API_BUSINESS_PARTNER` does for an identification's validity dates (seen on a response, [here](../finding_a_partner_by_identification/README.md)); for a property marked not nullable the same row is a conversion error. Mark date properties nullable unless the table guarantees a value.

## How to verify this in your own system

*Sure* means the claim is one the author would be surprised to see fail; *fairly sure* means it held in the releases the author knows and the detail may have moved; *from memory, check* means exactly that.

| Claim | Where to prove it | How sure |
| :-- | :-- | :-- |
| The four classes, model and service names the dialog proposes | `SEGW`, any project, *Generate Runtime Objects*: read the dialog before pressing OK | sure |
| A generated DPC method raises the not-implemented exception | `SE24` on the generated `_DPC` class, any `_GET_ENTITYSET` method | sure |
| The `_EXT` classes are not rewritten by generation | Add a comment to an `_EXT` method, generate again, read it | sure |
| An orphaned redefinition stops the `_EXT` class activating | Rename an entity set after implementing its method, generate, activate | sure |
| The Dictionary-to-EDM default mapping and facets | Import a structure with DATS, TIMS, CURR and CHAR 1 fields; read `$metadata` in `/IWFND/GW_CLIENT` | fairly sure on the facets |
| The entity set checkboxes become `sap:` attributes; which ones the runtime enforces | Uncheck *creatable* on a set and POST to it; uncheck *addressable* and GET it directly; read the two responses | from memory, check |
| `$filter`, `$top`, `$skip`, `$orderby` are not applied by the framework for a hand-coded set | A `GET_ENTITYSET` that selects everything; call it with `$top=1` | sure |
| `$select` is applied by the framework | The same method, called with `$select=` one property | sure |
| `$expand` calls the target set's method once per entity unless `GET_EXPANDED_*` is redefined | A breakpoint in the target's `GET_ENTITYSET`; a request with `$expand` on a set of ten entities | fairly sure |
| A CDS-referenced entity set pushes the options to the database | SQL trace (`ST05`) on a request with `$filter` against a referenced set | fairly sure |
| The two caches hold the old model after generation | Add a property, do not clear the caches, read `$metadata`; then clear both and read again | sure |
| The hub's URL uses the external service name | `/IWFND/MAINT_SERVICE`, the service's *ICF node* and *Call Browser* | sure |

## Provenance

Written from working knowledge of SAP Gateway on NetWeaver 7.4 to 7.5x and S/4HANA on premise, from memory: no SAP documentation was reachable from the session that wrote it (the help portal and the SAP Community are blocked by its network policy), and no claim was confirmed against a named system. The page started from screenshots of the Service Builder with the delivered project `API_BUSINESS_PARTNER` open, which confirm only what they show: the entity types of that project and their names. No message numbers are quoted. The program is a simulation of the rules stated here, not of SAP's generator.

## Po polsku, w skrócie

Projekt w SEGW to wyłącznie model danych: typy encji, ich klucze, zbiory encji, asocjacje i importy funkcji. Z tego modelu generator wytwarza cztery klasy: MPC, która odpowiada na `$metadata`, DPC z jedną metodą na każdy zbiór encji i każdą operację, oraz ich dwie podklasy `_EXT`. Cały własny kod trafia do klas `_EXT`, bo kolejne generowanie nadpisuje MPC i DPC, a `_EXT` zostawia bez zmian; stąd pułapka: po zmianie nazwy zbioru encji w `_EXT` zostaje redefinicja metody, której już nie ma, i klasa się nie aktywuje. Framework rozkłada adres URL na metodę i jej parametry, ale filtrowania, stronicowania i sortowania w ręcznie napisanej metodzie nie wykonuje nikt poza autorem; dopiero serwis oparty na widoku CDS przekazuje je do bazy przez SADL.

## Auf Deutsch: Stichwörter

Der Service Builder ist ein Codegenerator: das Datenmodell ist die einzige Quelle, MPC und DPC werden bei jeder Generierung neu geschrieben, und nur die `_EXT`-Klassen gehören dem Entwickler.
