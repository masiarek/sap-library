# Currency keys, codes and decimal places

**Level:** 101 · for anyone who has typed a currency code into SAP

**One line:** A currency in SAP is a three-character key in TCURC, and the number of decimals it shows is a separate fact in TCURX — which is why 1,000 JPY is stored as 10.00 and why every amount field has to carry its key.

## Three tables, three different facts

SAP keeps a currency in three small tables, and each one answers a different question.

| Table | Transaction | What a row says | Example |
|---|---|---|---|
| `TCURC` | OY03 | This key exists. It has an ISO code, an alternative key, an EMU indicator and a valid-to date. | `JPY` · ISO `JPY` |
| `TCURT` | OY03 (texts) | What the key is called, per language. | `JPY` · "Japanese Yen" |
| `TCURX` | OY04 | How many decimal places the key has, **if not two**. | `JPY` · 0 · `KWD` · 3 |

The key is what every amount field in the system refers to: BKPF-WAERS, BSEG-PSWSL, T001-WAERS, SKB1-WAERS and hundreds more are all `CUKY` fields whose values must exist in TCURC. The ABAP glossary calls the value a *currency key* and the set of valid values, held in TCURC, the *currency codes* ([currency key ↗](https://help.sap.com/doc/abapdocu_latest_index_htm/latest/en-US/ABENCURRENCY_KEY_GLOSRY.html)); in practice the two words are used interchangeably.

The ISO code column is there so that the SAP key and the ISO 4217 code are *allowed* to differ. They almost never do, and when they do it is deliberate: `USDN` is a five-decimal US dollar used for prices, and it maps to ISO `USD`. Interfaces that talk to banks and to other systems send the ISO code, not the key, and `BAPI_CURRENCY_GETDECIMALS` and the IDoc conversion modules read the mapping.

## Two decimals unless TCURX says otherwise

TCURX is deliberately short. A currency that is not in it has two decimals; that default is not stored anywhere. The rows that are there are the currencies whose smallest unit is the whole unit or a thousandth:

| Decimals | Keys delivered in TCURX (typical) |
|---|---|
| 0 | JPY, KRW, CLP, ISK, VND, PYG, UGX, XAF, XOF, XPF, KMF, DJF, GNF, RWF, BIF, VUV, and in SAP's delivery also IDR and TWD although ISO 4217 lists them with two |
| 3 | BHD, IQD, JOD, KWD, LYD, OMR, TND |
| 4 or 5 | Price currencies such as `USDN`, and any customer key created for unit prices |

Check the table in your own system rather than a list: SAP Note 137626 (*FAQ: Decimal places for currency codes*) is the authoritative discussion, and KBA 3556933 explains why you cannot simply give TWD or IDR two decimals once they are delivered with none.

## What the database actually holds

Every amount field in the ABAP Dictionary is a packed decimal with **two** decimal places, whatever its currency. For a currency with a different number of decimals the stored value is shifted so that it still fits:

> stored value = external amount × 10^(decimals − 2)

So 1,000 JPY is stored as `10.00`, 1.500 KWD as `15.00`, and 0.12345 USDN as `123.45`. The screen, the print program, the BAPI and the CDS view each undo the shift by looking at the currency key next to the amount, which is why an amount is never allowed to travel without its key. This is the *internal* representation; the amount a person reads is the *external* one. SAP Note 1240163 (*Amount too high by factor of 100 for HUF, JPY currencies*) and KBA 2123695 (the same factor of 100 in HANA Studio views) are the two commonest shapes of the bug that comes from forgetting it.

It is worth seeing once on a real document. The source document for this chapter shows a 100 USD posting in a JPY company code as `DMBTR 100,00` in the raw BSEG display: the field is JPY, so `100,00` means ten thousand yen. The program below reproduces the shift, the round trip, and the three plausible wrong numbers a report can print from one correct column.

## Consequences you meet in practice

- **Screens and reports.** `WRITE amount CURRENCY key` and string templates with `CURRENCY = key` apply the shift; a bare `WRITE amount` does not. See [Currencies in ABAP](../abap_currency_handling/README.md).
- **Interfaces.** An IDoc, a file or an OData payload carries external amounts. `BAPI_CURRENCY_CONV_TO_EXTERNAL` before sending and `BAPI_CURRENCY_CONV_TO_INTERNAL` after receiving (both unreleased but universally used, KBA 2659445), or the `CURRENCY_AMOUNT_SAP_TO_IDOC` / `IDOC_TO_SAP` pair, do the conversion.
- **CDS and HANA.** A CDS view declares `@Semantics.amount.currencyCode` on the amount and the framework shifts on output; the ABAP SQL function `CURRENCY_CONVERSION` has explicit `decimal_shift` and `decimal_shift_back` parameters. A native HANA calculation view has to be told about TCURX or it shows JPY a hundred times too small (KBA 2123695).
- **Changing the decimals of a live currency** changes the meaning of every stored amount in it. It is a data conversion, never a Customizing change: KBA 3369259 (*Change Decimal Places for a Currency Code*) says so, and the migration cockpit refuses three-decimal amounts outright (KBA 3517123).
- **Field length.** Because the shift multiplies a zero-decimal amount by 100 before storage, the ceiling of a 13-digit amount field is 100 times higher in JPY than in EUR. See [Rounding and the amount field](../rounding_and_amount_fields/README.md).

## Other things TCURC knows

- **Valid to.** A key can expire; VEF, HRK and ZWL have. Expired keys stay in the table because history refers to them.
- **EMU indicator.** Marks the legacy currencies that were fixed to the euro, so that triangulation through rate type EURX applies.
- **Alternative key.** A second, freely chosen key for the same currency, used by some interfaces.
- **Precious metals and funds.** XAU, XAG, XPT, XDR are currency keys too, and can carry amounts; a treasury system uses them.

A currency key on a G/L account (SKB1-WAERS) restricts the account: if it is not the local currency, only postings in that currency are allowed (message *Currency & not permitted in account*, KBA 2888262). The choice of local currency itself, and what it means for every line item, is the next page.

## How to verify this in your own system

| Claim | Where to prove it |
| :-- | :-- |
| A key exists, and its ISO code | `OY03`; `SE16N` on `TCURC`, fields `WAERS`, `ISOCD`, valid-to date |
| The decimals of a currency, and that absence means two | `OY04`; `SE16N` on `TCURX`, fields `CURRKEY`, `CURRDEC` |
| The stored value is shifted | `SE16N` on `BSEG` for a JPY line item, beside the same line in `FB03`: `WRBTR` reads the amount divided by 100 |
| The shift round-trips | `SE37` test of `BAPI_CURRENCY_CONV_TO_EXTERNAL` with 10.00 JPY, then `BAPI_CURRENCY_CONV_TO_INTERNAL` with the result |
| An account currency restricts postings | `FS03`, company code data, currency; post in another currency in `FB01` and read the message |
| Keys expire but stay | `SE16N` on `TCURC` for HRK or VEF, valid-to date filled |
